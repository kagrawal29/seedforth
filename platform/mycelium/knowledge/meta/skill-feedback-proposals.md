## P4: spec-to-ship — Simplify the Feature Completion Gate

**Pattern detected:** The completion gate (Phase 5, NO-SKIP) is skipped in 9/9 invocations (100% skip). Phase 5 itself is only reached 33% of the time. The gate is 10 fields long, some of which duplicate information already present in the Phase 4 review document.

**Evidence:** 0/9 traces contained "completion gate" or "feature completion gate".

**Current gate structure:**
```
SPEC: [path]
PLAN: [path]
FILES: [new + modified]
VERIFICATION:
  - primary: [pass/fail + timestamp]
  - tests: [pass/fail + counts]
  - validation: [pass/fail]
AGENT REVIEW: [path to review doc + status]
SPEC COMPLIANCE: [all criteria met / gaps listed]
EVIDENCE BASIS: [observed vs inferred]
AFTER: [what now exists]
RESIDUAL RISK: [what needs watching]
```

**Proposed change:**
- File: `.claude/skills/spec-to-ship/SKILL.md`
- Section: Phase 5 — "Feature Completion Gate [NO-SKIP]"
- Proposed (condensed to 5 required fields + 1 optional):
  ```
  SPEC: [path] — PLAN: [path]
  FILES CHANGED: [list]
  VERIFICATION: primary [✓/✗], tests [✓/✗ N passed], review [clean/resolved/escalated]
  SPEC COMPLIANCE: [all criteria met] or [gaps: ...]
  AFTER: [what now exists that didn't before]
  RESIDUAL RISK: [optional — anything that still needs watching]
  ```

**Rationale:** The current gate has redundant fields (EVIDENCE BASIS, separate AGENT REVIEW path). The condensed version keeps the 5 fields that answer "did it work" (spec, plan, files, verification, after-state) while cutting fields that duplicate the review doc. Lower friction = higher completion rate.

**Risk:** Medium. Shorter gate may miss edge cases. The EVIDENCE BASIS field (observed vs inferred) has real value for Track 3-equivalent work. Consider keeping it as an optional field for high-risk features.

## P5: architecture-validation — Replace social media guideline with explicit agent call

**Pattern detected:** Social media / practitioner verification (the key differentiating step in architecture-validation) has 0% adherence across all 5 observed arch-validation sessions. The step is currently written as a guideline to research agents: *"search practitioner accounts and forums, not just official docs."* It never fires as a distinct action.

**Evidence:**
- 5/5 traces with arch activity: no evidence of Twitter/Reddit/forum searches for production experience
- Teams deploy research agents (Sahiram 2026-04-10T16:42, Sahil 2026-04-11T11:27) but without the social media constraint

**Proposed change:**
- File: `.claude/skills/architecture-validation/SKILL.md`
- Section: "For open questions — deploy research agents"
- Current:
  ```markdown
  - [ ] **Include social media verification**: Each research agent should search practitioner accounts and forums, not just official docs. Vendor documentation hides reliability issues. Social media reveals them.
  ```
- Proposed:
  ```markdown
  - [ ] **Practitioner verification agent** [NO-SKIP for any OPEN decision]: Deploy a dedicated agent whose sole job is finding real-world production experience. Prompt it explicitly:
    > "Search Twitter/X, Reddit (r/devops, r/aws, relevant subreddits), Hacker News, and engineering blogs for people who have used [technology] in production. What problems did they hit? What were the failure modes? What would they do differently? Ignore official documentation entirely."
    
    This agent is separate from the technology/hosting research agents. Its job is adversarial — find what the docs hide.
  ```

**Rationale:** "Include social media verification" as a sub-bullet inside research agent instructions gets ignored because research agents interpret their goal as "answer the question" and official docs answer questions faster. Making practitioner verification a separate, mandatory agent with an adversarial prompt forces the distinct search behavior. Teams can still skip it if they explicitly mark the OPEN item as low-risk, but the default path now triggers it.

**Risk:** Medium. Adds a research agent call per open decision — could increase cost and time for large arch sessions with many open items. Consider adding "skip if decision is low-stakes (dev tooling, test utilities)" caveat.
